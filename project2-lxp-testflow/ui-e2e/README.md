# UI E2E 자동화 (Playwright)

엘리스 LXP의 핵심 사용자 흐름 7개를 실제 브라우저 UI로 검증한다. 테스트는 매번 빈 세션에서 폼 로그인부터 시작하며,
API는 쓰지 않는다. 시험 상태도 화면의 "테스트 재응시" 버튼으로 맞추고, 실패로 남은 데이터도 UI로 지운다.
저장 확인은 새로고침 또는 다른 역할로 재진입해 검증한다.

## 실행

> 공개본 안내: 원본은 팀 저장소 루트의 `part3_ui_automation/` 기준입니다. 대상 서버가 예시 주소라 그대로는 실행되지 않습니다.

이 폴더에서 `npm install` → `npm run install:browsers`(최초 1회) → `npm test`(시나리오 1~7, 10건) 순서이며, `npm run report`로 HTML 리포트를 엽니다.
계정은 `project2-lxp-testflow/.env`(utils/helpers.js 기준)의 `LXP_STUDENT_ID`, `LXP_STUDENT_PW`, `LXP_EDU_ID`, `LXP_EDU_PW`에서 읽고, 비밀번호는 Git에 넣지 않습니다.

## 전제 조건

- 대상: `web.example.invalid`, 클래스 3팀 전용 클래스, 과목 SANDBOX(731), 시험 차시 01 TEST(1585)
- `.env`의 학습자 계정은 위 클래스에 학습자로, 교육자 계정은 교육자로 가입돼 있어야 한다(학습자는 SANDBOX 과목 수강 상태). 특정 계정에 묶이지 않으므로 `.env`만 바꾸면 다른 계정으로도 실행된다.
- **01 TEST의 교육자 설정 "테스트 셀프 재응시 허용"이 켜져 있어야 한다.** 4번 시나리오가 이 버튼으로 응시 전 상태를 맞추고 끝낸다.
  꺼져 있으면 4번이 실패하며, 오류 메시지에 이 설정을 확인하라고 표시된다.
- 4번은 시작할 때 이전 실행이 남긴 상태를 UI로 되돌린다: 응시 완료면 "테스트 재응시", 시작 뒤 끊겨 응시 중이면 "테스트 이어하기"로 제출·종료까지 마친 뒤 재응시한다.
- 2-1은 실계정으로 실패 로그인을 1회 일으킨다. 계정 잠금 정책이 확인되지 않았으므로 연속 반복 실행은 피한다.

## 결과 확인

모든 테스트는 `test.step`으로 사용자 동작과 검증을 묶어 **메뉴 위치 → 클릭·입력 → 기대 결과** 순의 한국어 단계명을 남긴다.
HTML 리포트에서 테스트를 선택해 **Test Steps**를 펼치면 단계별 성공·실패와 소요 시간이 보이고, 실패한 단계에는 오류가 표시된다.
같은 화면의 **Screenshots**, **Videos**에서 화면과 실행 영상을 확인한다. 단계명에는 계정값을 넣지 않으며, 실계정 이메일·비밀번호는 `fill` 대신 `evaluate` 주입(`setValueQuietly`)으로 입력해 리포트 내부 데이터에도 값이 남지 않는다(Playwright는 `fill` 값을 `Fill "값"` 단계 제목으로 기록한다). 같은 이유로 `trace`는 켜지 않는다 — 켜면 evaluate 인자가 trace.zip에 남는다.

## 안전·안정성

- `workers: 1`, `retries: 0`: 순차 수행하며 상태 변경과 실패 로그인을 통째로 재실행하지 않는다.
- 화면 준비 지연은 Playwright 자동 대기와 제한된 조건 재확인(`expect().toPass()`)으로만 처리한다. 5xx API 요청을 재호출하지 않는다.
  고정 대기의 유일한 예외는 게시글 저장 전 500ms 정착 대기다(아래 구현 메모).
- 4번은 같은 학습자의 시험 상태를 바꾸므로 `.locks/`의 파일 잠금으로 같은 PC에서의 중복 실행을 막는다. 다른 머신과의 충돌은 담당자 1명 실행 규칙으로 막는다.
- 테스트 데이터 제목에는 실행 시각과 프로세스 ID를 붙이고, 실패한 테스트는 `afterEach`에서 새 세션을 열어 UI로 찾아 지운다. 정리 실패도 테스트 실패로 보고한다. 남은 데이터를 찾는 조회(게시글 검색 `/article?filter_title=`, 일정 `/schedule`·`/schedule/ics`·`/schedule/count`)가 4xx/5xx면 화면이 빈 목록처럼 보여도 '없음'으로 보지 않고 실패로 보고한다(dev 실측: 일정 조회 503에도 화면은 '예정된 수업 일정이 없습니다'). UI-TC-07의 삭제 일정 미노출 확인도 같은 감시를 거친다.

## 구현 메모

- 게시글 본문 에디터는 글자가 보인 뒤에도 잠시 폼 상태 반영이 늦어, 그 안에 저장하면 옛 본문이 전송된다. 그래서 입력 뒤 500ms 정착 대기 후 저장을 한 번만 누르고, 저장 요청의 `content`에 입력 본문이 실렸는지 함께 확인한다.
- 응시 완료 화면의 "테스트 재응시"는 `lecture/test/reset/by_self` API를 호출한다. part2 JMeter 시험 사이클의 재응시 단계와 같은 API다. org-api는 실패도 HTTP 200으로 주므로 화면 버튼만 보지 않고 응답 본문 `_result.status == ok`까지 확인한다(part2 판정과 같은 규칙).
- 잠금·재클릭·대기 처리의 세부 동작은 `utils/` 각 파일의 주석에 있다.

## 구조

- `tests/journeys.spec.js`: 시나리오 1~7 (2번은 4개 케이스)
- `utils/flows.js`: 로그인 이후 공통 UI 동작(과목 진입, 게시글 저장, 일정 CRUD, 시험 응시·재응시, 실패 잔여 데이터 정리, 로그아웃 등)
- `utils/helpers.js`: 대상 클래스룸·과목·차시와 폼 로그인
- `utils/lock.js`: 4번 시험 시나리오의 실행 잠금(`.locks/`, git 제외)
- `utils/video-reporter.js`: Playwright 영상을 TC 번호로 자동 복사. 실행된 TC는 영상이 없어도 같은 번호의 이전 영상을 먼저 지우고 `<TC>-<상태>.no-video.txt`를 남긴다(지난 실행의 passed 영상이 최신 결과로 오인되지 않게)
- `playwright.config.js`: 단일 워커, 무재시도, 영상·스크린샷·HTML 리포트 설정
- `ui_scenarios.md`: 시나리오 단계·화면별 기대 결과·추적성 표

## 산출물

- `test-results/`: Playwright 원본 영상·스크린샷·오류 문맥
- `playwright-report/`: HTML 실행 리포트
- `artifacts/videos/04-passed.webm`, `02-1-passed.webm` 등: 발표·제출용으로 TC 번호가 붙은 최신 영상
